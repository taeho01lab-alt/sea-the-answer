# 3단계 | DB 설계와 데이터 계약

## 왜 별도 스키마를 사용했나

기존 시제품의 가상 선박·운항 기록은 public 스키마에 있습니다. 새 실제 MRV와 합성 Noon을 기존 테이블에 바로 섞으면 기존 화면의 권한·계산 전제가 깨질 수 있습니다. 따라서 해사 데이터의 자료는 PostgreSQL의 maritime_data 스키마로 분리했습니다. 스키마는 하나의 데이터베이스 안에서 관련 테이블을 묶는 이름 공간입니다.

이 설계는 해사 데이터 범위의 6개 테이블 정의이며 기존 전사 19개 테이블 초안을 전부 대체하지 않습니다. 설계 문서는 docs/maritime-data/DATA_CONTRACT.md, 실행 가능한 DDL은 docs/maritime-data/schema.sql, 기계가 읽는 사전은 dictionary.json에 있습니다.

## 테이블의 역할과 관계

- source_files: 원본 파일의 버전·출처·해시·사용 목적을 저장합니다. 관측 데이터는 source_id로 이 테이블을 참조합니다.
- vessels: 실제 IMO와 가상 선박을 다른 접두어로 구분한 선박 식별자 목록입니다.
- annual_reports: 실제 MRV의 보고기간 단위 관측입니다. 연료, 보고 CO2, 운항시간, 추정거리, 품질과 출처를 저장합니다.
- synthetic_voyages: 합성 항차의 선박, 원본 항구 라벨과 최초·최종 보고일입니다. 실제 출입항 시각으로 해석하지 않습니다.
- synthetic_noon: 합성 일별 운항 관측입니다. 선박과 항차를 동시에 참조합니다.
- quality_issues: 레코드별 복구·검토·거절 사유입니다. record_id는 연간 또는 일별 테이블 중 하나를 가리키는 논리 참조입니다.

관계는 source_files에서 annual_reports·synthetic_noon·quality_issues로 이어집니다. vessels에서 annual_reports와 synthetic_voyages로, synthetic_voyages에서 synthetic_noon으로 연결됩니다. quality_issues의 record_id는 다형 참조이므로 일반 외래키 대신 적재 검증 SQL에서 존재 여부를 확인합니다.

## 타입과 제약을 정한 이유

연료·거리 등 수치는 PostgreSQL numeric으로 저장해 십진 정밀도를 보존합니다. 날짜는 date, 합성 관측 구간은 timestamptz, 원본 근거는 jsonb를 사용합니다. 기본키는 중복 저장을 막고 외래키는 존재하지 않는 선박·출처·항차를 참조하는 기록을 막습니다.

annual_reports에는 REAL:IMO: 접두어, 보고유형 FULL/PARTIAL/ARCHIVE_ANNUAL, 품질 상태 VALID/REVIEW/REJECT를 제한합니다. aggregate_eligible이 참이면 VALID이고 Partial이 아니어야 합니다. 시작일보다 종료일이 빠르면 거절합니다.

synthetic_noon에는 SYN: 접두어, 양수 DWT, 0 이상 거리·연료·속력, 0~24시간 기관 운전시간, 양수이면서 24시간 이내인 관측 구간 제약을 적용했습니다. 출처의 실제·합성 구분과 항차별 선박 일치는 교차 테이블 검증으로 추가 확인합니다. 모든 의미적 제약이 DDL 한 파일만으로 해결되는 것은 아닙니다.

## 조회 뷰와 인덱스

real_annual_query는 aggregate_eligible이 참인 실제 연간 자료를 제공합니다. development_noon_query는 VALID인 합성 Noon을 제공합니다. 일반 조회는 이 승인 뷰를 사용하므로 검토 대상이 실수로 기본 집계에 들어가는 것을 줄입니다.

선박·연도, 선박·날짜, 항차에 인덱스를 추가했습니다. 자주 사용하는 필터에 맞춘 조회 보조 구조이며 대규모 부하 목표 달성을 입증한 것은 아닙니다. 일반 사용자와 maritime_data 선박의 권한 매핑은 아직 없어서 조회 API는 관리자 전용입니다.

## 재현과 검증

scripts/describe_maritime_data.py는 전처리 코드의 FIELDS 정의에서 DDL·데이터 사전·문서를 생성합니다. 변경 시 생성 결과와 보관된 파일을 대조해 문서와 SQL이 달라지는 것을 막습니다. 이전 작업에서 세 출력의 일치를 확인했습니다. 단순 생성 명령은 CSV를 적재하지 않습니다. 기존 maritime_data에 테이블 생성 SQL을 다시 실행하지 마세요.

근거: scripts/describe_maritime_data.py, scripts/prepare_maritime_data.py의 FIELDS, docs/maritime-data/schema.sql, docs/maritime-data/DATA_CONTRACT.md. 실제 DWT·항구 매핑·공식 계수는 미확정이며 후속 보강 시 출처와 버전을 함께 설계해야 합니다.
